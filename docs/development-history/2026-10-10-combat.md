## 已完成：§2.2.2 冻结（水 + 冰）—— 剧变反应 + 碎冰接元素精通（2026-10-07）

新增 `A01A` 冰弹（`DataF = "freezingbreath"`，已反解确认进包），与火弹/水弹共用
`TestSkills_castElementBolt`。水 + 冰（**两个方向**）→ `reactionTable.FROZEN`
（`kind: "transform"`），在 `ElementalReactionSystem.resolve()` 里挂 `FreezeBuff`。

### 用户定的三个口径

1. **冻结时长由被消耗的元素量决定**：`frozenSeconds(consumed) = clamp(consumed × 2.5, 0, 8)`。
   2U 冰挨一发 2U 水 = 冻 5 秒。扣完才交给 `addFreezeBuff`，**韧性照旧生效**。
2. **碎冰随元素精通提升，走剧变曲线** `emTransform(EM) = 1 + 16·EM/(EM+2000)`
   （EM=0 → ×1.00，EM=200 → ×2.45，EM=1000 → ×6.33）。**不是**增幅的 `emAmplify`。
3. **碎冰的攻防类型表一起修**：冰爆改成 `registerSpellElement(..., "ice", 0, explosion)`
   走过的**声明基数**冰元素伤害 —— 打英雄不再被 ×0.5，且吃攻击者冰伤加成与目标冰抗。

### ⚠️ 本轮踩到的那个连接（再动要小心）

`DamagePipeline_dealElemental` 曾经把 `outcome.kind` **原样**透给 `dealRaw`。
冻结返回 `transform`，而 `dealRaw` 见到 `transform` 会**跳过元素加成 / 暴击 / 擢升** ——
照原样透传的话，那发水弹/冰弹打出冻结的同时**自己也退化成裸伤**，不崩不报错只是数字对不上。
现在钉成只有 `amplify` 透传，`DealInput.kind` 的语义收窄为
「**这一段伤害**被反应改成什么样」，与「触发了哪一类反应」（`ctx.reactionKind`）彻底分开。

### 结构变化

- `AMPLIFY_TABLE` → **`REACTION_TABLE`**（它现在装得下非增幅的反应）；`ReactionDef` 加
  `kind: ReactionKind` 与 `control?: "freeze"`；`ratio` 变成可选（剧变反应没有倍率）。
- `reactionMultiplier` 的 `transform` 分支从 `emAmplify` 改成 `emTransform`（今天不可达，
  留给 D+ 阶段「剧变反应自身的伤害段」）。
- `registerSpellElement` 的守卫从 `gauge <= 0` 放宽到 `gauge < 0` ——
  **`gauge = 0` 是「只声明元素、不附着」**（`resolve()` 对它本来就是早退）。

      冻结期间目标身上是干净的（`consumeRatio = 1.0`，来袭元素也不附着）。
      要做「冻着也能继续反应」得让 `FreezeBuff` 自己携带元素量。
- [ ] **`FreezeShatterSystem` 不区分冻结来源**（两层冻结一起碎）——

## 已完成：§2.2.2 剧变反应「雷元素三兄弟」（2026-10-07）

超载（火+雷，2.0）/ 超导（冰+雷，0.5）/ 感电（水+雷，1.2）三条全部落地，两个方向同 id。
新增 `A01B` 雷弹（`DataF = "chainlightning"`，已 `w2l.exe lni` 反解确认进包），
与火/水/冰弹共用 `TestSkills_castElementBolt`。

### 用户定的口径：**等级基数表**

剧变伤害 = `transformBase(触发者等级) × ReactionDef.transformCoeff × emTransform(EM) × (1−抗性) × (1−免伤)`。
`transformBase(lv) = 12 + 6×(lv−1)`（Lv1 = 12、Lv10 = 66；lv ≤ 0 或非整数一律按 1 级）。
**不吃**元素伤害加成、暴击、擢升 —— 由 `dealRaw()` 里 `kind === "transform"` 那条分支保证。

⚠️ **`transformBase` 读的是触发者（施法者）的等级，不是目标的** —— 与原神口径一致，
也与 `FreezeShatterSystem` 读攻击者 EM 一致。

### 结构变化

- `ReactionDef` 加 `transformCoeff` / `damageElement` / `effect`；**`control` 改名 `effect`**
  （它现在要装「击退」「削甲」「持续伤害」，再叫 control 就是下一个人的坑）。
- 新文件 **`src/system/element/ReactionEffects.ts`**（落地效果 + AoE 枚举）与
  **`ReactionBuffs.ts`**（`SuperconductBuff` 削甲、`ElectroChargedBuff` 本仓第一个 DoT buff）。
- 打通「剧变伤害段」：`PendingSpellElement.kind` + `registerSpellElement` 第 6 参 +
  `DamagePipeline_dealElemental` 尾参 `segmentKind`。默认值让两个既有调用点一个字不用改。
  `DealInput.kind` 的三值语义至此**两半都齐了**：`none|amplify` 说「来袭那一击」，
  `transform` 说「剧变反应自己造的那一段」—— 是同一句话的两半，不是推翻上一轮。

### ⚠️ 为什么 `dispatch` 是注入的（再动要小心）

`ReactionEffects` 需要 `ElementalReactionSystem` 的两个能力，但**不能 import 它** ——
会造 `ElementalReactionSystem → ReactionEffects → ElementalReactionSystem` 的 require 环。
tstl 的 import 是**加载期解引用**（`local X = ____m.X`），环里读到的是半成品 → `X` 恒 `nil`
→ 运行时「attempt to index a nil value」。所以反过来：由系统实现 `ReactionDispatch`
接口并把自己的 `this` 传进去。`StunBuff.ts:33` 为同一个坑留过说明。

### ⚠️ 踩到的两个坑

1. **tstl 把「存进类成员的函数」当方法**。`private readonly pulse: () => void` +
   `this.pulse = pulse` + `this.pulse()` 会编成 `self:pulse()`（把 `self` 当第一个参数传），
   而注入的是无 `this` 的闭包 → **编译期** TSTL 错
   `Unable to convert function with no 'this' parameter to function with 'this'`。
   修法是把类型写成 **`(this: void) => void`**（字段与构造参数都要），tstl 才知道它是普通函数值。
   报错位置指的是**赋值那一行**，不是调用点 —— 别看错地方。
2. **AoE 的 `IsUnitEnemy(u, owner)` 里的 `owner` 必须是施法者的玩家，不是目标的**。
   传目标的话：主目标自己会被排除（它不是自己的敌人）⇒「超载了但目标不掉血」，
   而**施法者本人**会被圈进受害者名单 ⇒「超载把自己炸飞」。两种表现都不报错。

### ⚠️⚠️ 本轮挖出的硬事实：DoT 实际跳数没有干净公式，必须实测

`ElectroChargedBuff.tick()` 是 `nextTickAt = this.elapsed + 间隔`，而 `BuffManager`
以**固定 0.1s** 累加 `elapsed`。浮点误差让跳点整体偏移，偏移量还随跳数累积 ——
所以**不能按「时长 ÷ 间隔」算**，也没有一个跨间隔通用的公式。

间隔 1.0 时（感电用的那档）表现为「首跳落在 `elapsed ≈ 1.1`」：`0.1` 累加十次是
`0.9999999999999999`，**小于 1.0**，那一步跨不过 `nextTickAt = 1.0`。于是
`duration` 秒只有 `ceil(duration) − 1` 跳：

| `duration` | 跳数 | 时刻 |
|---|---|---|
| 1.0 / 1.5 / 2.0 | **1** | 1.1 |
| 2.5 | **2** | 1.1 / 2.1 |
| 4.0 | **3** | 1.1 / 2.1 / 3.1 |
| 8.0 | **7** | 1.1 … 7.4 |

⟹ **`ElectroChargedBuff` 类注释里原来那句「共 4 跳、合计 5 段」是错的**（实际 3 跳 4 段），
2026-10-09 加燃烧时才实测订正。**只订正注释、行为一个字没改** ——
改行为等于凭空给感电 +20% 伤害，那是单独一轮的事。

间隔 0.6 时（燃烧用的这档）反而**完全规整**：`0.6 × k`。

| 时长 | 跳数 | 总伤 | 对应草量 |
|---|---|---|---|
| 1.5（下限） | **2** | 1.0× | < 0.75U |
| 2.0 | 3 | 1.5× | 1U |
| 3.0 | 5 | 2.5× | 1.5U |
| **4.0** | **6** | **3.0×** | **2U（草弹，常规）** |
| 5.0 | 8 | 4.0× | 2.5U |
| 8.0（上限） | 12 | 6.0× | 4U |

**验证方法**：写个和 `BuffManager.tick` 同构的模拟循环（`elapsed += 0.1`，
跨过 `nextTickAt` 就记一次并推进），比在游戏里数跳数靠谱得多。

⟹ **`BURNING_MIN_SECONDS` 必须大于一个跳间隔**：时长短于间隔时**一跳都跳不出来**
⟹「燃烧触发了、飘了字、伤害为零」。而所有查表断言全绿 —— 静默失效。
纯函数层有一条 `MIN > TICK` 的正面断言钉着它。
1.5 留足浮点余量，且纯函数层有一条 `MIN > 1.0` 的正面断言钉着。

## 遗留（控制效果那一轮留下的）

- [ ] **`MaxUnitSpeed`（默认 400）是同族的第二个静默钳子，只是方向朝上**。
      `SetUnitMoveSpeed` 写超过 400 的值会被钳到 400，而 `StatSheet.lastSynced` 记的是
      算出来的 final（比如 520）—— 于是「表里 520、引擎里 400」，面板撒谎、不报错，
      和刚修好的 `MinUnitSpeed` 一模一样。现在没有把移速堆过 400 的来源所以还没炸，

      `writeNative` 里把钳制后的值回写 `lastSynced`。

      **2026-10-07 更新：这条**没有**被漂移治理顺带修掉。** 那轮的「写后读回」
      是按 `isDriftSlot` 卡着开的 —— 折算与读回共用同一份名单，理由是「对不参与折算的
      槽位读回没有收益，只会把『引擎没接受我们的写入』变成每次标脏都重写一遍的写战」。
      `MOVE_SPEED` 不在名单里，所以 `lastSynced` 记的**仍然**是「我们想写的值」（520），
      面板**照旧撒谎**。

      `maxunitspeed` 一起放开。仍然排在那条「让 `MOVE_SPEED` 只有一个写入方」后面。

- [ ] **让 `MOVE_SPEED` 只有一个写入方**（用户 2026-10-07：**做技能时真撞上再搞**）—— 根治「冲刺/击退会冲掉减速、禁锢」的唯一方向。
